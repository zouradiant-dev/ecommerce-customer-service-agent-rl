# 在线 SFT 的 Bad Case 诊断与提示词对照

后续进展：[失败诊断与定向 SFT 数据准备](online-repair-sft-and-diagnostics-20261013.zh-CN.md) 已完成；以下保留提示词对照阶段的原始结果和当时的未完成事项。

2026-10-13，在用户已启动的 Featurize 4090 推理服务上完成开发诊断。网页、评测脚本和隔离模拟业务数据库在本机；每次模型生成实际调用远端 BF16 v18 SFT。没有训练、改权重、使用正式 test 或接入真实支付。

## 1. 从十个失败定位问题

首轮十五题的十个失败都涉及所需取消预览缺失。九题只调用 list_orders 后结束；change_target 第二回合能预览新目标，但第一回合没有创建旧目标预览，后续确认旧申请无法验证失效逻辑。

模型已经能读出“无线耳机对应 order_A”，却因为用户还有键盘等订单，继续要求指定具体订单。这是可复核的轨迹现象，不是十种独立系统故障。预览缺失进一步使确认、重复确认、状态竞态、过期、提交后丢响应、结果未知及重启场景无法完成；不能据此宣称这些真实模型恢复路径已通过。

提出三个待验证假设：商品到订单 ID 的绑定不足；把所有订单当成候选而过度澄清；新四工具/按钮确认协议与旧离线训练分布不一致。业务执行检查、按钮确认和幂等规则保持原样，不由评测器替模型生成预览。

## 2. 五个版本的实际结果

原十五个 dev 用例、实际模型、BF16、贪心解码、8192 输入预算、六个最近回合和业务期望不变。policy.py 保留 baseline_v1，候选可通过 CLI 显式选择，默认网页未切换。

| 配置 | 改动 | 完整执行 | 实际结果 |
| --- | --- | --- | --- |
| baseline_v1 | 原提示词与描述 | 15/15 | 5/15 |
| binding_prompt_v2 | 只改提示词，明确匹配、预览与只读重试 | 13/15 | 已执行部分 3 题通过；完整通过率未知 |
| binding_tools_v2 | 只改工具描述，说明 product/id 和预览语义 | 15/15 | 5/15 |
| binding_combined_v2 | 同时改提示词和描述 | 15/15 | 5/15 |
| binding_compact_v3 | 更短的匹配/预览补充，描述不变 | 2/15 | 已执行部分 1 题通过；完整通过率未知 |

三个完整配置通过的是同样五题，没有配对净改善。工具描述修改增加了调用数：原方案 48 次模型/18 次工具，只改描述 51/21，组合修改 50/20。

两组不完整实验因模型请求被 HTTP 422 拒绝而停止，summary 中通过率为 null，不能用已执行子集比例替代完整成绩。短提示词的基础取消题成功，但第二题被拒绝，所以没有据此上线。对第二题仅重放一次模型请求、未执行业务工具，复现 422，返回 inference_or_tool_parse_failed，输入 1026 token；健康检查仍可读。当前远端错误码没有细分解析、推理或资源异常，也没有返回原始生成，因此此处不武断认定具体失败原因。

同批 case 哈希一致，实际提示词/工具哈希均保存。过程中新增 compact_v3 后，组合与短版本的 policy.py 源文件哈希变化，但已有四个版本实际 prompt/schema 没变；comparison.json 显式列出 source_differences，不声称所有源码完全相同。这些是探索性开发对照，不是正式显著性证明。

另一次独立基线重跑为 6/15，本轮主对照和首轮为 5/15。未定位这一题波动的全部原因，不能把单次小幅变化当成可靠提升。

## 3. 扩展十二题，防止只调原题

在候选得分出来前构造了 data/online-binding-dev-v2.jsonl：新商品电动牙刷/旅行箱/床头灯、新订单号 R-*，覆盖名称、简称、改称、明确 ID、同名商品按金额澄清、无匹配、仅查询、已发货、撤回、改目标、未付款无退款与他人订单。

各题使用独立新业务数据；expected 与 smoke fixture 不进入模型上下文。增加中间状态 checkpoint，避免“第一回合误选订单，第二回合纠正后最终状态正确”被算作整题通过。checkpoint 是评测断言，不是 Agent 可用工具。构造器有输入校验，只修改每题新建的模拟数据库。

| 配置 | 扩展 dev 结果 |
| --- | --- |
| 原方案 | 7/12 |
| 提示词＋描述 | 8/12 |

组合修改改善 new_product_exact 和 product_paraphrase，但让 unpaid_no_refund 从通过变成失败，简称、撤回、改目标仍失败。净多通过一题不足以支持上线，尤其存在未付款场景回退。这十二题是补充开发回归，不是冻结独立 test。

## 4. 两个小诊断

移除结构化记忆、切换 full-history，在基础取消/重复确认/读取超时恢复三个 dev 场景仍为 0/3，不能把问题简单归咎于记忆提示。这不是完整记忆策略泛化对照。

同一个“取消电动牙刷”请求和同一目标订单，在扩展集合中有三笔本人订单时失败；只移除无关本人订单、保留该目标和他人订单后，原方案成功创建预览并完成模拟取消，1/1。现象支持继续排查多订单匹配，但单样本不能证明机制或泛化能力。

人工复核还发现短语验证器会把“已经取消取消请求”误当成“订单已取消”。本轮保留原评分规则和原记录，单独记下误判；该题同时缺少第一回合预览，去除这个短语误判也不会使整题通过。后续需区分撤回申请与取消订单，继续防范虚假成功，不能只删除失败断言提高分数。

## 5. 当前决策与下一步

保留网页原方案。没有能同时改善原集合、扩展集合和调用稳定性的候选，不发布未验证改动，不增加自动预览来给模型补分。

下一步先补推理失败的分类和受控原始输出诊断，定位 422 的具体原因；严格解析和写入规则仍保持。再构造新四工具协议的针对性 SFT 轨迹与对照，优先包含：

- 相同取消意图对应零/一/多笔匹配，订单总数与目标候选数交叉组合。
- 商品简称、改称、同名多单按金额澄清；不能把旧测试 ID 或商品写进提示词。
- 用户明确取消→读取当前详情→创建预览→按钮确认后收到服务端结果；文字确认不能伪造按钮授权。
- 仅查询、撤回、改目标、未付款、已发货、越权、只读失败恢复，以及合法原生工具调用格式。

以上是待生成/验证的数据设计，不宣称已经有新训练集或已训练提升。先冻结独立 test 的表达和业务组合，再进行小规模补 SFT；优先评测旧能力回退、新协议任务完成与格式失败，暂不进入 RL。两轮提示词试验未改善不等于已经证明 SFT 到瓶颈。

python scripts/build_binding_dev_cases.py

数据已存在时构造器拒绝覆盖；直接使用该 JSONL 即可。输出目录也必须是新目录。遇到模型请求失败，批处理停止并保留结果；可单独运行 evaluate_online_agent.py 指定 profile，不能把未完成运行当完整对照。

本轮主结果在 outputs/online-policy-factorial-20261013-r2，扩展结果在 outputs/online-binding-guards-20261013-r1。comparison.json 汇总完整性、配对改善/回退、哈希和源码差异。每题保留 history/events/spans/state，完整输出不上传 Git。

工程验证：32 项原会话测试、18 项记忆/评测测试、26 项部署测试、8 项策略/扩展验证和 3 项只读比较器验证，共 87 项相关测试通过。Smoke 的脚本替身只证明运行时与断言，不代表实际 SFT 成绩。模型与工具依然是单 Agent，本轮没有引入 RAG、多 Agent 或新训练算法。
