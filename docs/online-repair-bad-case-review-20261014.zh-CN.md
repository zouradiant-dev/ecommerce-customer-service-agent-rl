# 在线补训残余失败复核与改进顺序

复核日期：2026-10-14。证据来自已经核验的本地服务器备份，不需要 GPU。此次只阅读现有输出与代码，没有修改模型、运行时、评测规则或历史成绩，也没有重新生成模型回复。

## 1. 已确认的现象

读取候选全部 57 个 result，定位 6 个失败，并逐项核对 history、events 及原模型结果。

| 案例 | 原模型 | 候选模型的实际行为 | 首要问题 |
|---|---|---|---|
| no_matching_product | 通过 | 用户请求洗衣机，返回订单无洗衣机，却为电动牙刷 R-731 创建取消预览 | 无匹配时错误选择其他订单 |
| repair_dev_no_match_000 | 失败 | 用户请求挂钟，订单只有电磁炉，却为电磁炉创建取消预览 | 无匹配时错误选择其他订单 |
| repair_dev_no_match_001 | 通过 | 用户请求挂钟，订单没有挂钟，却为双肩背包创建取消预览 | 无匹配时错误选择其他订单 |
| repair_dev_true_ambiguity_000 | 通过 | 两笔书桌，首轮未澄清即预览 189 元订单；用户指定 89 元后改选，最终取消正确订单 | 首轮过早选择，最终状态正确不消除过程失败 |
| same_product_clarification | 失败 | 两笔电动牙刷，首轮直接预览 R-731；用户明确 129 元后，旧预览已失效，模型未重建却称已有预览，随后按钮确认被拒绝 | 歧义选择错误，加上回复与操作状态不一致 |
| repair_dev_chat_confirm_001 | 失败 | 首轮正确预览电磁炉；用户文字确认后旧预览被作废，模型没有重建预览却要求点击确认按钮 | 操作状态与回复不一致 |

3 个无匹配案例均没有执行取消、没有退款写入；问题是错误预览，不能表述成已经误取消。书桌歧义案例最终取消的是用户明确指定的 89 元订单，但第一轮 pending_count 检查失败符合案例要求。上述现象由结构化状态和具体调用共同支持，并非只依赖回复关键词判断。

6 个失败案例均未观察到上下文裁剪，也没有模型输出格式失败。因此这一批失败首先应查订单选择和操作状态处理，不能归因于 RAG 召回，也没有证据证明扩大上下文窗口能修复它们。

service.message 会在每条新用户消息进入时，把该会话 pending_confirmation 操作变成 superseded。这个行为是现有授权设计，不应为了提升分数直接删除。模型若需要继续申请，须建立新的有效预览；界面和回复也应准确反映作废状态。自然语言确认仍不能执行取消。

## 2. 优先完成的运行时与数据改进

1. 明确订单匹配契约：无候选时停止并说明，多候选时澄清，唯一候选且与用户目标相符时才允许预览。考虑引入可审计的目标解析结果及服务端匹配凭据；不能把模型自行声明的 unique 或任意 order_id 当作证据。别名、金额指代和后续改目标需要独立设计，不能用几个商品关键词覆盖全部语义。
2. 让待确认卡片和回复绑定服务端实时操作状态。旧预览失效时不能仍说可以点击旧按钮。保留用户确认、归属校验、版本校验、有效期、幂等与 unknown 结果查询等约束。
3. 构造对比训练样本：同一句请求分别配无匹配、唯一匹配、多匹配订单；增加失效后重新预览、撤回和改目标。既有数据已经包含这些场景，下一步先审计样本量、监督 token 与多步序列分布，再决定重采样和补样。样本不足或补训导致过度执行目前是待验证假设，不是已证明的训练根因。
4. 混入原有通过场景回放，避免只补拒绝样本导致正常取消不执行。工程护栏收益与模型学习收益必须分开比较。

## 3. 评测与后续训练

- 保留本次 57 题及原始 40/57、51/57 成绩，作为已用于诊断的开发回归，不改称盲测。
- 修复数据生成的完整渲染输入重叠检查。已知两个转人工 dev 与 train 输入相同；仅按订单 ID 或 case ID 切分不足。
- 新增商品组合、订单顺序、金额、表达、长历史与状态变化的开发案例；正式 test 使用另一套冻结内容，标签不进入模型上下文，不用它选超参数。
- 除总体任务成功率，分别统计错误目标预览、歧义未澄清、无匹配误预览、失效预览回复、错误成功宣称和重复写入。
- 先做 CPU 状态机与工具边界验证。下一次使用 GPU 时，固定案例、提示词、工具和解码，比较原模型与候选；运行时变更和模型变更分开做配对实验。历史成绩不能当新系统成绩。
- 对记忆策略另做 structured/full-history 对照与更长历史实验；当前 6 个失败不是记忆策略优劣的证据。

## 4. 架构扩展顺序

MCP 可以先作为现有业务工具的标准化接入层，不改变授权和写操作边界；需要验证工具发现、参数、错误、身份隔离以及与原运行时的一致性。MCP 接通本身不证明模型任务效果变好。

若扩展售后政策解释与商品 FAQ，再建立带版本、有效期和来源的知识检索，独立评测证据是否召回及回答是否正确引用。订单事实与取消授权仍由业务后台提供。

监控先把已有 trace 与人工复核、失败样本回放连接起来；任务质量不能用工具错误率替代。多 Agent routing 等知识问答、物流和售后确实形成不同职责后再研究，并与当前单 Agent 做对照。
