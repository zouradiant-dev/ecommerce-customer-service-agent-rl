# v18 项目问题、解决方案与交接记录

更新日期：2026-10-04

## 2. 问题一：奖励与沟通评测既漏判，也可能误放行

### 现象

早期验证器对同义表达召回不足，例如“原支付路径”“已为您升级人工”“已经退过款”等真实语义可能被判失败；另一方面，错误退款 ID、退货 ID 冒充退款 ID、金额单位错误或没有工具证据的成功声明也可能得到过高分。

### 根因

- 自然语言关键词规则没有充分处理否定、条件、未来计划、引用和跨句事实。
- 沟通语义与工具证据没有严格绑定。
- 退款、退货、工单等不同 ID 类型缺少显式事实校验。
- 旧奖励把某些任务要求的正确重试误判为无意义循环。

### 解决方案

- v12–v17 将语义修正做成显式版本，不覆盖旧结果。
- 新增基于成功工具结果的 ID、金额、支付渠道和状态校验。
- 对否定、假设、引用、未来承诺和矛盾表达补充反例测试。
- v18 将最终成功拆成数据库状态、必需工具、调用顺序、政策、结构化终态和沟通六类证据。
- 正式验收使用 `strict_binary_v18`；训练可使用 `train_shaped_v18`，危险行为固定为 `-1`。

### 经验

评测器修正只能称为重评分，不能称为模型提升。必须保留原始回复、工具轨迹和旧分数，并记录哪些行只改变了派生字段。

## 3. 问题二：v17 GRPO 的 dev 改善没有泛化

### 现象

v17 最终冻结 test 中，原 SFT 和探索性 GRPO checkpoint-25 都是 48/160（30.0%）；配对差值为 0，bootstrap 95% 置信区间为 `[-0.05, 0.05]`。GRPO 在少数场景得分增加，却在政策绕过等安全场景退化。

### 根因

- train/dev 与最终 test 的场景家族错位。
- 复杂多订单、身份失败、订单归属和跨订单商品绑定主要依赖模型隐式学习。
- 严格 0/1 奖励导致同组样本经常全 0 或全 1，GRPO 没有相对优势信号。
- 训练连续出现无方差 batch 后正确触发保护停止，只留下探索 checkpoint。

### 解决方案

- 不晋升该 GRPO checkpoint，不把负结果包装成 RL 成功。
- v18 重建覆盖 30 个场景的 train/dev，并在模板和状态命名空间上隔离。
- 把身份、订单归属、写操作前置条件和工具终止条件下沉到不可绕过的业务状态机。
- 保留严格最终指标，同时用安全约束下的分解奖励产生训练信号。
- 只有 mixed-group rate、关键工具覆盖、人工奖励校准和非零梯度资格检查全部通过后，才允许重新进入 GRPO。

## 4. 问题三：模型把有限状态业务流程当作自由文本规划

### 现象

模型在简单单订单流程表现尚可，但在以下组合任务中不稳定：

- 身份连续失败后没有升级人工；
- 未先 `list_orders` 就读取或修改订单；
- 商品不属于目标订单仍尝试退款；
- 没有用户确认就执行写操作；
- 工具已失败却声称取消、退款或改址成功；
- 人工升级成功后继续调用工具。

### 解决方案

新增 `CustomerServiceToolsV18` 和证据绑定状态机：

1. 身份失败次数受限，达到上限后只暴露人工升级。
2. 身份成功后必须先列出本人订单，再读取具体订单。
3. 写操作只允许作用于已读取、属于当前用户且满足政策的对象。
4. 退款前必须核对订单与商品项绑定，并取得允许退款的政策结果。
5. 所有写操作要求真实用户消息中的明确确认。
6. 人工升级成功后关闭后续工具面。
7. 结构化终态的 `action_taken` 和 `action_id` 必须由本轮成功写工具举证。

语言模型继续负责理解请求、抽取参数和生成用户可读说明；控制层负责身份、权限、顺序和安全边界。

## 5. 问题四：首台 GPU 实例出现权重数据完整性异常

### 现象

首台 RTX 4090 48G 实例在没有前向、反向和优化器更新时，完整基础模型经过 GPU 路径后出现 3,072 个错误元素。磁盘 safetensors SHA256 和 CPU 加载均正确，错误值仍为有限数，因此普通 NaN/Inf 检查无法发现。

### 排查过程

- 先后检查 BF16、FP32、SDPA、eager、梯度检查点、梯度累计、独立 FP32 缓冲等路径。
- 对四个模型分片核对官方 SHA256。
- 对 CPU 模型与磁盘逐元素比较。
- 分别测试 `device_map` 直接加载和 CPU 加载后整体上传 GPU。
- 将 GPU 权重拷回 CPU 做逐位核验，而不只做有限性检查。

### 结论与处理

问题发生在训练之前，继续调整学习率或累计策略无法解决。更换实例后，同一基础模型的 7,615,616,512 个参数元素在两种加载路径、前向前后均逐位一致，随后 smoke 和 full 正常完成。

### 经验

- 训练前检查必须包含模型权重 CPU/GPU 往返一致性。
- “没有 NaN”“没有 OOM”不等于硬件路径正确。
- 发现训练前数据损坏时应立即更换实例，不应继续消耗预算调参。

## 6. 问题五：离线实例无法从 Hugging Face 补齐基座文件

### 现象

更换实例后，评测器曾报错无法连接 Hugging Face，并且本地缓存中缺少 `Qwen/Qwen2.5-7B-Instruct` 的 `config.json`。adapter 只包含 LoRA 权重，不能独立替代基座模型。

### 解决方案

- 使用包含完整基座缓存的镜像或实例。
- 固定基座 revision，记录缓存与 tokenizer 校验。
- 使用 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1` 时，启动前先运行缓存预检。
- 模型备份和代码备份分开保存；LoRA adapter、tokenizer、配置与训练记录必须一并归档。

## 7. 问题六：训练损失很低不等于训练异常，也不等于泛化良好

### 现象

追加训练从已训练 adapter 继续时，首批 train loss 已非常低；后续 loss 接近零。与此同时，小规模目标场景可以快速达到满分，但宽场景能力可能退化。

### 解释

- adapter 已经在确定性参考轨迹上训练过，继续学习高度相似的 assistant token 时交叉熵自然很低。
- assistant-only loss 只监督助手 token，不能直接衡量工具策略、状态安全或场景泛化。
- 数据重复、目标分布过窄会让 loss 继续下降，同时产生灾难性干扰。

### 解决方案

- 不用 train loss 选择最终模型。
- 每个 checkpoint 必须跑按场景切片的严格 dev。
- 保留原始 adapter，追加训练输出写入新目录。
- 目标场景改善必须同时满足非目标场景不回退和 `hard=0`。

## 8. 问题七：追加 SFT 出现灾难性干扰

### 现象

为修复 `contradictory_order`、`cross_order_item_mismatch` 和 `refund_quantity_exceeds`，先后尝试 supplement、rebalance 和 full replay。定向小样本可以满分，但其他场景出现明显回退，例如已取消订单、正常取消和数量退款之间相互覆盖。

### 根因

- 目标数据比例过高，模型学到局部决策捷径。
- 多个场景共享相似工具序列和终态标签，少量追加训练会改变已有边界。
- 用 5 题或 15 题筛查选择 checkpoint，方差和覆盖不足。

### 处理

- 所有追加训练版本均未替代原始 adapter。
- 原始 adapter 作为稳定基线保留。
- 转向模型外 policy controller，优先用确定性证据修正安全边界。

## 9. 问题八：r4 定向全过，但宽测严重回退

### 定向结果

r4 在 7 个目标场景的 35 题筛查中达到 35/35，跨订单商品完整 20 题也达到 20/20、`hard=0`。这一结果不足以证明整体能力。

### 宽测结果

在 30 个场景、每类 5 题的 150 题宽测中：

- r4：111/150（74.0%），`hard=6`；
- 同一批任务对应的原始 adapter 历史轨迹：134/150（89.33%），`hard=3`；
- 逐题使用相同任务 ID 和相同随机种子；
- 96 题共同通过，15 题由 r4 改善，38 题由通过变失败，1 题共同失败。

### 主要根因：提示词漂移

原始 adapter 使用 `ecommerce_cs_agent_v18_structured_terminal` 训练。r4 评测时，为了补充新的 decision 枚举和说明，换成了 `ecommerce_cs_agent_v18_structured_terminal_r2`。权重哈希没有变化，但模型输入合同已经变化；在贪心解码和相同 seed 下，工具调用路径仍发生了系统性改变。

因此，“原模型”不能只表示 adapter 权重不变，还必须同时冻结：

- 基座 revision；
- adapter 哈希；
- tokenizer 与 chat template；
- system prompt；
- 工具 schema；
- 解码参数与 seed。

### 次要根因：终答重写丢失必要语义

r4 在 `late_refund` 中用工具消息覆盖模型原说明，保留了“超过 30 天退货期限”，却丢失了“当前不能退款”的明确拒绝表达，导致 5/5 被判缺少 `return_window_expired` 意图。

反事实重评分表明：在 r4 已生成的工具轨迹上，未经控制器重写的原始终答只有 95/150；控制器重写后为 111/150。控制器整体净救回 16 题，只直接改坏 5 题。r4 的主要损失发生在模型推理阶段的提示词漂移，而不是控制器整体思路无效。

### 安全兜底缺口

如果没有命中特定证据规则，r4 会原样放行模型终答。身份工具异常的 5 题和物流状态的 1 题出现了没有成功写工具却声称执行动作的结构化终态，形成 6 个 hard failure。

### 测试设计问题

35 题筛查没有覆盖身份工具异常、多订单批量取消、多订单消歧、部分退款、持续工具异常和物流状态，因此出现典型的定向选择偏差。

## 10. r5 的修复

r5 已完成以下本地修改：

1. 新增冻结的训练提示词常量；启用 policy controller 时强制使用 adapter 训练时的原始提示词。
2. `protocol.json` 和逐条 rollout 记录实际使用的 prompt version。
3. 退款政策拒绝时优先保留模型原说明，并保证包含“不能/无法退款”和“未执行退款”的明确语义。
4. controller 版本升级为 `ecommerce_cs_policy_controller_v18_r5`。
5. 风险筛查从 7 个场景扩展到 14 个场景、70 题。
6. 保留 30 场景、150 题宽测脚本。

本地验证：

- v18 契约测试 26 项通过；
- evaluator 与 local-HF 回归测试通过；
- `--validate-only` 确认 controller 为 r5、提示词为原始训练版本、150 题任务计划完整；
- r5 打包内容和包内文件哈希通过读取校验。

r5 尚未进行真实 GPU 模型评测，不能标记为正式版本。

## 11. 无 GPU 时项目如何使用

无需模型即可运行环境和网页审计演示：

```powershell
python scripts\run_local_demo.py --output outputs\local-demo-release --replicas 1
python scripts\run_web_demo.py --port 8765
```

浏览器访问 `http://127.0.0.1:8765`。该模式展示数据库、工具执行、状态变化、验证器和奖励分解，不把确定性 reference 或 weak baseline 冒充训练模型。

真实 Qwen2.5-7B LoRA 推理仍需要以下任一算力来源：

- 本地可容纳 4-bit 7B 的 GPU；
- 临时 GPU 实例；
- 支持该 LoRA 的 OpenAI-compatible 推理服务。

CPU 可以继续完成文档、数据生成、业务逻辑、验证器、控制器和回归测试，但不适合实时运行 7B 模型。

## 12. 下一次 GPU 验证计划

下一次开卡不需要重新训练，先验证 controller：

1. 核对基础模型 revision、adapter SHA256、tokenizer 和 prompt version。
2. 运行 70 题风险筛查。
3. 要求 `worker_errors=0`、`max_step_exhaustions=0`、`hard=0`，且关键场景不低于原始 adapter。
4. 风险筛查通过后运行 150 题宽测。
5. 150 题至少不低于原始同题基线 134/150；建议晋升门槛为至少 135/150，且 `hard=0`。
6. 通过后再运行完整 600 题；不得根据最终 test 调整提示、规则或 checkpoint。

若风险筛查未达到门槛，保留原始 adapter，继续在 CPU 侧修改通用安全兜底，不再做新的针对性补训。

### 2026-10-05 r5 GPU 风险筛查结果

r5 在 RTX 4090 上完成 14 场景、70 题筛查：`59/70`（84.29%）、`hard=0`、
`worker_errors=0`、`max_step_exhaustions=0`。按此前同场景前 5 题的原始 adapter
结果统计，原始约为 `39/70` 且 `hard=6`；因此 r5 消除了该筛查集的 hard failure，
并增加 20 条严格通过，但仍未达到放行条件。

11 条失败集中在三处：

- `partial_quantity_refund` 为 `4/5`：成功退款终态缺少精确金额和剩余数量；
- `persistent_tool_error_escalation` 为 `0/5`：模型已经连续查询失败两次并成功转人工，
  r5 却把“没有成功的 `get_order`”误判为“从未尝试读取”，在转人工后额外补了一次
  已不可用的 `get_order`，制造 `tool_not_available_in_current_state`；
- `refund_quantity_exceeds` 为 `0/5`：用户使用“一件/两件”等中文数量表达，r5 只解析
  阿拉伯数字加“件”，所以没有把模型自造的 `DUPLICATE_*` 决策统一为
  `QUANTITY_REJECTED`。

r6 保留 r5 的缺失读取补全，但收紧为“从未尝试目标订单读取且尚未成功执行写操作”时
才补读；同时支持中文件数、扩展退款意图识别，并用实际工具输出补齐退款金额与剩余件数。
这些修改只依赖用户消息和工具证据，不读取场景名、期望答案或隐藏评测字段。

r6 本地 v18 契约测试 29 项通过。RTX 4090 上的 70 题风险筛查达到 `70/70`、
`hard=0`；随后 150 题宽测达到 `149/150`（99.33%）、`hard=0`、
`worker_errors=0`、`max_step_exhaustions=0`。唯一失败是
`duplicate_refund_request` 的终态标签错成 `ALREADY_REFUNDED`，没有安全违规。
该结果超过预设的 `>=135/150` 且 `hard=0` 放行门槛，下一步运行冻结的完整 600 题 dev；
完整 dev 结果生成前仍不把 r6 标记为最终版本。

- `.safetensors`、`.pt`、`.sqlite`、日志和压缩包；
- 可由脚本重新生成的 v18 数据目录；
- `packages/` 下的服务器部署副本和重复数据。

## 15. 最重要的工程经验

1. 原模型基线必须冻结完整推理合同，不能只冻结权重。
2. 定向小样本全过不能替代宽场景回归。
3. 安全 Agent 的成功必须由状态和工具证据决定，不能相信模型自报。
4. 评分修正、控制器修正和模型训练是三类不同变化，报告时必须分开。
5. train loss 不能替代业务 dev 指标。
6. 任何追加训练都必须与原始 adapter 配对比较，并检查非目标场景。
7. GPU 训练前要验证权重数据完整性，不能只检查 OOM 和 NaN。
8. 失败实验应保留并写明原因；负结果比未经验证的“提升”更有价值。
