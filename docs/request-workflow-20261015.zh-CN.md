## 实现

新增显式选择的 `binding_state_v8`，原 v7 提示词及解析路径继续保留。

1. **分句角色与目录解析分离。** `request_workflow.py` 保留每个分句的取消、保留、查询、展示角色、商品提及原文和位置，再对本人实时目录解析候选。简称来自有边界的商品后缀及受控别名；同后缀匹配多笔时保留全部候选。不会按相似度挑第一笔，也不会把“有线耳机”直接当成“无线耳机”。
2. **请求框架持久化。** `request_intents` 表按会话和请求保存原文哈希、上轮请求框架、当前解析与目录快照。待选择、待按钮确认、撤回、查询、否认分别处理。确认卡失效后，明确继续仍可引用当前有效请求并重新创建卡；撤回、查询、失败轮和未知新商品不能借用旧取消请求。
3. **写权限独立。** 请求框架只支持预览规划。模型调用预览时，服务端再次解析本轮原文与前一框架，读取实时本人目录，并核对唯一目标、版本、商品、金额和状态。实际取消仍由用户按钮、订单版本与幂等接口约束；模型不能修改框架或通过填写字段授权取消。
4. **事实由服务端展示。** `order_facts.py` 用整数分格式化金额，工具同时返回 `paid_amount_yuan`。同名订单澄清列表与明确的订单事实查询最终由服务端生成，避免模型把513.02元说成51.30元。回复事实有单独的控制器追踪，不能算模型生成质量提升。
5. **检索和过滤可区分。** `policy_evidence.py` 在三类已配置演示主题内按概念识别问答，减少依赖固定词序；保留原始召回、选中文档和过滤文档。追踪仅记录主题数、召回数、选中数、过滤数和无依据原因，不把用户正文写入监控。未知的运费、保修等政策继续无依据拒答。
6. **限制模型恢复与转接。** 普通文本里的工具JSON会被拒绝执行，最多要求模型纠正一次，另计协议重规划。人工接管必须有当前用户明确请求。只读问答以原始用户查询的证据为准，模型额外工具轮次最多一轮，避免重复检索或错误改写查询覆盖已有证据；截断后展示原文的动作单独计数。

这仍是确定性的有限解析器与单进程 SQLite 原型，并未实现通用语言理解、学习得到的意图模型或任意企业知识库问答。模型目前仍负责原五工具协议中的规划。是否引入额外模型抽取，需要在这个工程基线之后另做消融，不能把确定性解析包装成大模型语义抽取。

## 网页模型联调：已完成

第三套Test完整落盘后，第一次网页检查的第三轮请求因实例余额耗尽关闭而超时。该失败轮、追踪和作废申请原样保留，不删除也不改成成功；没有产生取消或退款。随后通过新SSH端口24566恢复推理，核对模型ID、适配器、基座版本、tokenizer及BF16精度与冻结Test一致，在独立新会话完成网页冒烟检查。

1. “不是我要取消耳机，请先保留这笔订单”：没有创建取消申请或写账本。当前回复仍是泛化的澄清句，未作为客服体验优秀的证据。
2. “耳机留下，键盘这笔不买了”：只显示键盘order_B的299.00元确认卡，耳机仍已付款。
3. “我确定要取消这笔订单，请重新显示确认卡”：沿用同一请求目标，作废旧卡并生成新卡；文字确认后仍无取消和退款。
4. 点击“确认取消”并接受确认框：仅键盘取消，耳机保留；账本恰有一次取消和一笔29900分的pending退款。
5. 刷新网页后，订单、聊天及处理进度恢复。随后模型回复“订单已取消，退款处理中，尚未确认到账”，没有把申请提交说成资金到账。

验收记录为 `outputs/request-workflow-demo-20261015-r1/browser-verification.json`，截图为该目录的 `browser-completed.png` 与 `browser-order-result.png`。本次检查覆盖真实模型与本机模拟订单接口，不涉及真实资金；只验证页面刷新恢复，未在本次浏览器冒烟中重启服务进程。这些网页请求不并入第三套60题成绩。
