# v17 最终 Test 失败复盘与 v18 改进计划

记录日期：2026-10-03。

本文冻结记录 v17 最终 test 的结论、失败原因和下一版改进路线。它不会改写已经观察过的 test、模型、评分规则或原始轨迹，也不把负结果包装成 RL 成功。任何 v18 改动都必须使用新版本数据和新的冻结 test-v2；v17 test 只保留为历史基准。

## 一、结论

探索性 GRPO checkpoint-25 没有在最终 held-out test 上优于原 SFT。两者都是 48/160（30.0%），配对差值为 0，bootstrap 95% 置信区间为 `[-0.05, 0.05]`，不显著。GRPO 不满足模型晋升条件，正式 RL Gate 仍未通过，两个模型都不具备生产上线证据。

这不是一个无效项目：项目已形成完整的数据库状态环境、工具审计、SFT/GRPO 训练、冻结评测、配对统计、失败恢复和可复现备份。正确的项目结论是“探索性 RL 的 dev 增益未泛化到新场景家族”，而不是“RL 提升了最终效果”。

## 三、最终结果

### 3.1 总体比较

| 指标 | 原 SFT | GRPO checkpoint-25 |
|---|---:|---:|
| 通过数 | 48/160 | 48/160 |
| Pass@1 | 30.0% | 30.0% |
| 仅该模型通过 | 9 | 9 |
| 两者共同通过 | 39 | 39 |
| 两者共同失败 | 103 | 103 |

GRPO 相对 SFT 的净提升为 0。160 道配对任务中有 142 道结果相同，只有 18 道发生胜负交换，说明 checkpoint 主要改变了少量局部行为，没有形成稳定能力提升。

### 3.2 分场景结果

| Test 场景 | 原 SFT | GRPO | 结论 |
|---|---:|---:|---|
| `cancel_after_shipment` | 17/20 | 17/20 | 相同 |
| `cross_order_item_mismatch` | 0/20 | 0/20 | 共同失败 |
| `duplicate_refund_request` | 8/20 | 9/20 | GRPO +1 |
| `final_sale_refund` | 16/20 | 17/20 | GRPO +1 |
| `identity_mismatch` | 0/20 | 0/20 | 共同失败 |
| `mixed_order_bulk_cancel` | 0/20 | 0/20 | 共同失败 |
| `order_not_found` | 0/20 | 0/20 | 共同失败 |
| `policy_bypass_request` | 7/20 | 5/20 | GRPO -2，安全场景退化 |

GRPO 在两个简单拒绝/幂等场景各增加 1 题，却在政策绕过场景减少 2 题。总分打平且安全场景退化，不能晋升。

### 3.3 失败组件

| 失败组件 | 原 SFT | GRPO |
|---|---:|---:|
| 状态错误 | 31 | 32 |
| 策略错误 | 25 | 25 |
| 必需工具错误 | 76 | 82 |
| 沟通语义错误 | 110 | 112 |
| 错误工具选择 | 76 | 82 |
| 重复工具循环 | 21 | 21 |
| 过早写操作 | 9 | 8 |
| 未知工具 | 6 | 7 |

GRPO 的必需工具失败和错误工具选择均比 SFT 多 6 次，说明最主要的问题不是回答文风，而是工具规划和执行协议没有泛化。

## 四、失败原因

### 4.1 缺少确定性的业务流程控制

当前把身份重试、订单归属、前置查询、写操作授权和终止条件主要交给模型自行判断。对简单单订单流程尚可，对组合任务不稳定：

- 身份不匹配：两模型都可能连续调用身份核验直到 20 步上限，没有转人工；20/20 未创建要求的工单。
- 混合订单批量取消：20/20 没有先执行要求的 `list_orders`；有些样本用 `get_order` 后直接写入，触发 premature write。
- 订单不存在：部分样本直接 `get_order`，没有用订单列表确认归属；另一部分虽正确停止，但沟通评分器仍漏判。
- 跨订单商品：大量样本未调用必需的 `search_refund_policy`，且没有稳定绑定订单与商品项后停止退款。

这些是有限状态流程问题。继续让语言模型从提示词中隐式学习，成本高且安全性差。

### 4.2 Train 与 Test 的场景家族完全错位

v17 dev 的 7 个场景是地址修改、已取消订单、矛盾订单、延迟退款、未确认退款、签收前退款和超数量退款；最终 test 的 8 个场景则是发货后取消、跨订单商品、重复退款、不可退商品、身份不匹配、批量取消、订单不存在和政策绕过。场景名称与组合流程均不重合。

因此，dev 上原 SFT 97/140、GRPO 106/140 的 6.4 个百分点差异，没有转化为新场景家族的泛化提升。当前 test 更接近 OOD challenge，而不是与训练同分布的普通 held-out test。

### 4.3 严格二值奖励导致 GRPO 零方差

v13 每题生成 4 个 completion，但训练奖励只有严格 0/1。当同组全部失败或全部成功时，组内相对优势为零。实际训练连续三个生成 batch 没有组内奖励差异后按保护规则停止，只留下 checkpoint-25；未完成原计划的 100 步。

这个停止是正确保护，不能删除。失败说明任务难度、采样分布与奖励粒度没有形成可学习信号。增加步数或更换显卡不会自动修复零方差。

### 4.4 沟通评分器召回不足

冻结的 v17 正式分数必须保留，但轨迹显示评分器仍存在明显漏判：

- 回答已经写明“订单不在列表中、无法取消、未进行操作”，仍被标记缺少 `order_not_found` 和 `no_operation_executed`。
- 回答已经写明“定制商品不可退、政策不允许、未执行退款”，仍被标记缺少拒绝意图。
- 回答已经写明“已发货，不能直接取消”，仍被标记缺少 `shipped_order_cannot_cancel`。
- 回答明确指出商品项属于另一订单且停止退款，仍可能被标记缺少不一致/未执行意图。

原 SFT 有 34 题、GRPO 有 30 题仅沟通组件失败，而状态、策略和必需工具均已通过。若只用于诊断并忽略沟通组件，硬执行通过数分别为 82/160（51.25%）和 78/160（48.75%）。这不是新的正式成绩，但说明 30% 同时包含模型失败与评分器漏判。

v17 在最终 test 中改变了 37 条失败解释，但奖励翻转为 0，说明此前的语义扩展没有覆盖新的 held-out 表达。不能在看过本次 test 后继续修改 v17 并重算正式分数。

### 4.5 评测规模与执行限制

最终 test 只有一次 greedy trial，没有多 seed 或多采样稳健性结论。加速交接使用了两个并发 GPU 进程完成剩余 149 条记录，单对话仍为 batch size 1、模型和协议未变，但没有逐位等价基准。这不会自动否定结果，却属于报告必须披露的复现限制。

## 五、v18 改进设计

### 5.1 用状态机保证安全和工具顺序

新增模型外业务控制层，至少实现：

1. 身份失败最多 1～2 次；随后仅允许 `escalate_to_human`，屏蔽订单写工具。
2. 多订单请求必须先 `list_orders`，再逐订单读取和判断；写操作只能作用于已核实且政策允许的订单。
3. 订单不存在时先用本人订单列表确认；未找到即进入 `ORDER_NOT_FOUND` 终态，禁止猜测或替代目标。
4. 退款前验证 `order_id` 与 `item_id` 归属，并执行政策查询；不一致即进入 `ITEM_ORDER_MISMATCH` 终态。
5. 所有取消、退款、地址修改使用动作白名单和前置条件；策略拒绝后屏蔽相关写工具。

模型仍负责请求理解、参数提取和自然语言回复；控制层负责不可绕过的身份、归属、顺序和权限。这是业务 Agent 的安全边界，不等于用规则替代整个模型。

### 5.2 增加结构化终态，降低文本评分脆弱性

模型最终结果采用可校验结构，例如：

```json
{
  "decision": "ORDER_NOT_FOUND",
  "action_taken": false,
  "message": "未在您的订单列表中找到该订单，因此没有执行取消操作。"
}
```

`decision` 只有在数据库状态、成功工具调用和权限证据一致时才有效；模型不能通过自报标签获得奖励。核心任务成功由状态、工具和结构化终态联合判断，自然语言完整性单独评估。

建立独立人工校准集，覆盖肯定、否定、引用、假设、未来计划、第三人称陈述、同义词和跨句指代。语义评分器在启用前应达到至少 95% precision 和 95% recall；校准集不能包含 test-v2。

### 5.3 重建 v18 数据划分

- v17 test 已经查看，永久封存，不能进入训练、dev、模板选择或超参数选择。
- 为全部核心流程生成新的 train/dev 样本，覆盖简单任务和多条件组合任务。
- 每类建议至少 100～200 个不同状态实例，包含成功、拒绝、工具瞬时错误、持久错误和反例。
- 同一业务场景内按模板或生成器族隔离 train/dev/in-domain test-v2，避免近重复泄漏。
- 另设 OOD challenge-v2，专门放未见组合和表达；不得与普通 in-domain test 混成单一分数。
- test-v2 必须在最终模型、提示、评分器和生成协议冻结后才能打开。

### 5.4 先重新训练 SFT

SFT 训练样本必须显示完整工具顺序、终止原因和最终结构化决策，重点补充：

- 身份失败转人工；
- 多订单部分执行；
- 订单不存在且禁止替代操作；
- 跨订单商品绑定；
- 重复退款幂等；
- 不可退商品和政策绕过；
- 工具超时重试一次后升级；
- 错误工具、越权写入和内部 ID 幻觉的负例。

先在新 dev 上比较 checkpoint。若 SFT 尚未稳定解决工具流程，不允许进入 GRPO；RL 不应承担补齐基础流程知识的职责。

### 5.5 将训练奖励改为安全约束下的分解奖励

最终验收继续采用严格全通过，但训练阶段使用分解奖励产生组内差异。建议初始形式：

- 身份、归属、越权或危险写入：硬门控，整条奖励记为 `-1`；
- 最终数据库状态：0.35；
- 必需工具与调用顺序：0.25；
- 政策判断：0.20；
- 结构化终态：0.10；
- 用户沟通：0.10。

奖励版本必须重新命名、做正反例单元测试，并由人工同时抽查正奖励和负奖励。不能把 test-v17 的具体答案、task ID 或 verifier 私有意图写入提示或训练数据。

完整规范见 [v18 奖励机制设计](reward-v18-design.md)。该设计明确区分正式评测用的 `strict_binary_v18` 与训练用的 `train_shaped_v18`，并规定危险行为 `-1` 硬门控、非安全失败的奖励上限、结构化终态证据、反奖励攻击约束、人工校准、组内方差准入及统一严格评测。奖励实现是 v18 的前置里程碑，不是训练脚本中的附属参数。

### 5.6 RL Gate 与正式 GRPO

进入 GRPO 前必须满足现有工程门槛：

- 工具格式稳定率至少 98%；
- 关键工具成功覆盖完整；
- SFT 最近 3 个 checkpoint 的 pass rate 波动不超过 0.02，确认进入平台期；
- 至少 60% 的剩余失败属于可由策略优化的失败；
- 至少 20% 的同题采样组同时出现成功与失败；
- train 分组完整，无 worker error、非法调用、截断和 max-step 耗尽；
- 三个关键写工具都存在严格通过轨迹；
- 正负奖励人工审阅通过，动态 sampler 与真实 TRL 训练环境分别验证。

先跑 10 步资格验证，检查有限非零梯度、LoRA 张量变化、冻结参考不变、显存余量、保存和重新加载。资格验证通过后再跑 50～100 步；连续三个无方差 batch 仍应停止并保留现场。

## 六、v18 晋升标准

以下是下一版项目验收提议，不追溯改变 v17：

1. 身份、订单归属和政策绕过场景不得出现危险写操作。
2. in-domain test-v2 目标至少 75%，期望达到 80%。
3. OOD challenge-v2 目标至少 50%，期望达到 60%。
4. GRPO 相对同版本 SFT 至少提高 5 个百分点。
5. 配对 bootstrap 95% 置信区间下界必须大于 0。
6. 任一安全关键场景不得相对 SFT 退化。
7. 至少两个训练 seed 结论方向一致；资源允许时完成三个 seed。
8. 不根据 test-v2 结果更换模型、checkpoint、提示、评分器或阈值。

若未达到这些条件，保留 SFT 作为研究基线，不晋升 RL 模型；项目仍可报告负结果。

## 七、实施顺序与成本边界

1. 本地 CPU：状态机、结构化终态、评分器校准和测试。
2. 本地 CPU：生成并验证 v18 train/dev，冻结但不打开 test-v2。
3. 48G GPU：一轮新 SFT，先做短验证再完整训练。
4. CPU/GPU：奖励采样和人工审阅，正式通过 RL Gate。
5. 48G GPU：10 步 GRPO 资格验证，再进行 50～100 步训练。
6. GPU：完整 dev 选择并冻结模型；最后仅运行一次 test-v2。

按当前 3 元/小时的历史单价，若环境可由私有镜像恢复，新增 GPU 阶段初步预留 20～35 元；这是规划估计，不是平台报价、完成承诺或自动租卡授权。CPU 改造应先完成，避免带着已知零方差和流程缺陷继续计费。

## 八、当前决策

- v17 test、模型和评分结果永久只读保留。
- 不晋升 GRPO checkpoint-25，不声称正式 RL Gate 通过。
- 不继续扩展同一 v13/v17 实验或在旧 test 上追分。
- 下一版本从 CPU 侧的状态机、结构化终态、评分器校准和数据重建开始。
- 在新的 SFT 达标且奖励 Gate 通过前，不启动新的 GRPO。

## 九、2026-10-03 实施更新

CPU 第一阶段已完成并保持 opt-in：

- `CustomerServiceToolsV18` 强制身份核验、本人订单列表、订单读取、商品归属、政策允许和用户确认的顺序；身份连续失败两次后只保留人工升级，人工升级成功后关闭工具面。
- 结构化终态只接受精确 JSON 对象；`action_taken`、`action_id` 与决定标签必须由本轮可信工具证据支持，协议标签本身不能满足自然语言沟通评分。
- `strict_binary_v18` 用于最终验收，`train_shaped_v18` 用于训练；危险写入、伪造成功和伪造动作 ID 直接得到 `-1`。
- 校准脚本根据人工审阅轨迹、组内方差、沟通 precision/recall、关键写工具覆盖和源码 SHA256 生成 `reward_calibrated`，不能通过手写布尔值放行。
- 新增 10 个 v18 契约测试；全仓回归共 247 项通过，另有 1 项可选 LangGraph 测试因依赖未安装而跳过。
- 已生成独立 v18 train/dev：3,000/600 个任务，覆盖全部 30 个场景，提示家族和状态命名空间隔离，test 行为 0，未复用 v17 test。
- 确定性参考控制器为全部 3,600 个任务生成严格通过轨迹，形成 14,800/2,960 条 train/dev assistant-only SFT 样本；这些样本明确标记为非学习模型结果。
- 48G 配置已固定基础模型提交、数据哈希和 20 步 smoke→925 步 full 门禁；便携包 `packages/v18-sft-48gb-r1.tar.gz` 已通过包内预检。当前尚未在 GPU 上启动 SFT，尚未完成人工奖励校准，也没有启动 GRPO；test-v2 未生成或打开。
